## BULGULAR

### Yeni Bulgular

#### R91-01: `translationSchedulerBusy()` Defensive Catch Tutarsızlığı
**Dosya:** `src/browser-tab-resources.js:3-12`
**Tür:** Kod Kalitesi (Düşük Risk)
**Öncelik:** P3
**Açıklama:** Scheduler'da beklenmeyen hata durumunda `true` (busy) dönüyor. Bu, scheduler'da bir hata olması durumunda kullanıcının sekmesini asla unload edememesine yol açar. Ancak bu defensive bir karar — scheduler'ın iç durumu bilinmediğinde unload etmekten kaçınmak (busy varsaymak) da mantıklı.
**Kanıt:**
```js
function translationSchedulerBusy(scheduler) {
  if (!scheduler) return false;
  try {
    const state = scheduler.snapshot();
    return (Array.isArray(state?.pending) && state.pending.length > 0)
      || (Array.isArray(state?.queued) && state.queued.length > 0);
  } catch (_) {
    return true;  // Hata durumunda unload'ı engelle
  }
}
```
**Öneri:** Mevcut davranış kabul edilebilir (defensive). Düzeltme gerekmiyor.

#### R91-02: `SafeSecretStore.save()` Temp Dosya Temizliği
**Dosya:** `src/secret-store.js:166-192`
**Tür:** Kaynak Yönetimi (Teorik)
**Öncelik:** P3
**Açıklama:** `finally` bloğunda temp dosya siliniyor, ancak rename başarısız olduğunda temp dosyası diskte kalabilir. `try` bloğu `renameSync`'ten sonra `return` ediyor, finally çalışıyor, ama `temp` artık `undefined` değilse silme çalışır. Bu doğru davranış. Ancak `mkdirSync` veya `writeFileSync` sırasında exception olursa `temp` henüz atanmamış olabilir. `if (temp)` kontrolü var, bu yüzden güvenli.
**Kanıt:**
```js
const dir = path.dirname(this.filePath);
temp = path.join(dir, `.${path.basename(this.filePath)}.${process.pid}.${Date.now()}.tmp`);
// mkdirSync burada exception fırlatırsa temp = null kalır, finally'de if (temp) korur
this.fs.mkdirSync(dir, { recursive: true });
```
**Öneri:** Mevcut kod güvenli. Düzeltme gerekmiyor.

#### R91-03: `OutputTransaction.stage()` `PipelineCancelled` Yayılımı
**Dosya:** `backend/pipeline_control.py:245-251`
**Tür:** Doğru Davranış Doğrulaması
**Öncelik:** Bilgi
**Açıklama:** `except BaseException:` bloğunda stage başarısız olduğunda rollback yapılmadan sadece başarısız entry temizleniyor. Bu doğru çünkü `PipelineCancelled` (iptal) bir hata değil, beklenen bir sinyal. Ancak bu blok aynı zamanda gerçek exception'ları da yakalıyor ve yeniden raise ediyor — yani transaction'ın bütünü iptal olmuyor. Bu, birden fazla output yazılırken biri başarısız olursa diğerlerinin korunmasını sağlıyor. Doğru tasarım.
**Kanıt:**
```python
except BaseException:
    # Opsiyonel bir çıktı (dual/rapor) hata verdiğinde çağıran bu hatayı
    # uyarıya çevirebilir. Yalnız başarısız stage'i düşür; transaction'ın
    # tamamını kapatmak daha önce hazırlanmış sağlam çıktıları yok ederdi.
    _cleanup_entry_files(entry, keep_final=True)
    if self.entries and self.entries[-1] is entry:
        self.entries.pop()
    else:
        self.entries = [row for row in self.entries if row is not entry]
    self._persist()
    raise
```
**Öneri:** Doğru tasarım. Düzeltme gerekmiyor.

## MİMARİ DEĞERLENDİRME

### Güçlü Yanlar

1. **Güvenlik katmanları (olağanüstü):**
   - `settings-security.js`: 2000+ satır, prototype pollution koruması, sır redaksiyonu, atomik yazım, JSON şekil doğrulama, deep merge güvenliği
   - `secret-store.js`: OS safeStorage şifreleme, mirror backup, partial decryption koruması
   - `atomic-json.js`: PID'li temp dosya ile atomic rename, mirror backup politikası
   - `pipeline_control.py`: 7 aşama × 5 nokta cancellation checkpoint, owner_pid ile cross-process koruma

2. **Hata yönetimi (tutarlı):**
   - Tüm `try/catch` bloklarında anlamlı fallback
   - `try { ... } catch (_) {}` kalıbı yalnızca görmezden gelinebilir hatalarda
   - Promise rejection'lar context-aware (B83-31: `emitResult` try/catch)

3. **Race condition koruması:**
   - `serializeWatchMutation`: promise zinciri ile sıralı yazım + `baseItemRevision` taşıma
   - `invalidateBy`/`recoverOutputTransactions`: `owner_pid` ile cross-process koruma
   - `_pid_is_alive`: Windows'ta ctypes ile gerçek exit code kontrolü
   - `flushBrowserCaptureQueue` ve `flushWatchLibraryBeforeClose`: kapanışta senkron flush

4. **Async timeout/dispose:**
   - `withTimeout`/`withAbortTimeout` ortak yardımcı (CDP sızıntısı çözümü)
   - `withBrowserCompatibilityHost` ve `invalidateBy` ile generation tracking

5. **Konfigürasyon güvenliği:**
   - `PERSIST_VALUE_CONTROLS` ve `PERSIST_CHECKBOX_CONTROLS` listeleri birebir senkron
   - `UI_ENUMS` ve `UI_NUMERIC_RANGES` ile enum/sayısal doğrulama
   - `ENDPOINT_PRESETS` ile izinli endpoint listesi

### Dikkat Çekici Alanlar (Düzeltme Gerektirmeyen)

1. **Ölü kod (zararsız):** `pipeline_control.py` Windows'ta ölü `os.kill(pid, 0)` çağrısı var (önceki dallarda erken return). Bakım kolaylığı için silinebilir, ama işlevsellik etkilenmiyor.

2. **Mikro-optimizasyonlar:** SponsorBlockCache `delete` + `set` yerine doğrudan `set` kullanılabilir. Harita zaten aynı anahtarı üzerine yazar.

3. **Defensive catch:** `translationSchedulerBusy` hata durumunda `true` dönüyor. Scheduler'ın iç durumu bilinmediğinde unload etmekten kaçınmak için kabul edilebilir.
